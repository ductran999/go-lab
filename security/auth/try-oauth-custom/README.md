# Why need oauth 2

- Want Social Login (google, facebook, github, etc) -> Let Other Provider authorized our app to access user data
- Develop ecosystem (Google, Facebook, Github, etc) -> Provide OAuth 2.0 to let other app access user data

## Why Oauth + Proof Key for Code Exchange (PKCE) - Pronunciation: "pixie"

- Mitigate the risk of having the authorization code intercepted by a malicious app

- state: avoid CSRF attack, but not enough to prevent code interception. force full flow is send from one user.
- code_challenge + code_verifier: (Commitment Scheme) (Challenge - Response mechanism)
  - code_verifier: (or secret) generated by client and send to authorization server.
  - code_challenge: (lock) generated by client and send to authorization server with challenge_method (hash_method).
  - AuthServer: will verify code_verifier with code_challenge when client exchange token pairs.
- authCode: generated by the authorization server return to client. Client use this code to exchange token pairs.

## Public Client (Unauthenticated Client)

- Vue, React, Mobile, SPA, etc. (No Client Secret) -> Cause reverse client code can get `client_secret`.

## Confidential Client

- Server, Backend, etc. (With Client Secret) -> Can store `client_secret` in server side (in environment variable, config file, etc.) and not expose to public.

## OAuth 2.0 + PKCE Flow

```mermaid
sequenceDiagram
    autonumber
    actor User as User
    participant FE as Frontend (React/Mobile)
    participant Server as Auth Server (Go/Google)

    %% Step 1: Generate Secrets
    Note over FE: --- STEP 1: GENERATE CRYPTO SECRETS ---
    Note over FE: 1. Generate random 'state' (save to sessionStorage)<br/>2. Generate random 'code_verifier' (save to sessionStorage)<br/>3. Hash 'code_verifier' (SHA-256) -> 'code_challenge'

    %% Step 2: Authorize Request
    Note over FE, Server: --- STEP 2: SEND Signature & CSRF STATE ---
    FE->>Server: GET /oauth/authorize?code_challenge=hash_xyz&state=secret_abc123...
    Note over Server: Server remembers the 'code_challenge' (The Lock)<br/>and mirrors the 'state'

    %% Step 3: Authenticate
    Note over User, Server: --- STEP 3: AUTHENTICATE ---
    User->>Server: Login & grant permission
    Server-->>FE: HTTP 302 Redirect with 'code' and 'state'

    %% Step 4: Client-side CSRF Check
    Note over FE: --- STEP 4: CLIENT-SIDE CSRF VERIFICATION ---
    Note over FE: Compare incoming 'state' from URL<br/>with stored 'state' in sessionStorage

    alt State Mismatch (Potential CSRF Attack)
        Note over FE: Abort flow immediately! (Do not exchange code)
    else State Matches (Secure Session)
        %% Step 5: Token Exchange
        Note over FE, Server: --- STEP 5: EXCHANGE CODE WITH VERIFIER ---
        FE->>Server: POST /oauth/token (code=xxx & code_verifier=my_secret_key)
        Note over Server: Server hashes 'code_verifier' (SHA-256)<br/>and compares with stored 'code_challenge'

        alt PKCE Verification Matches
            Server-->>FE: Return Access Token (JWT)
        else PKCE Verification Fails
            Server-->>FE: Reject Token Request
        end
    end
```
